# Open Questions and Future Iterations

- [x] ~~Observability destination~~ - resolved: CloudWatch Logs Insights for v1, not Datadog. Datadog has no meaningful free tier for log ingestion/indexing (only a 14-day trial and a free Infrastructure-only plan that excludes logs entirely), so it isn't viable as an always-on destination for a personal project. CloudWatch Logs Insights is free at this volume and automatically discovers fields from structured JSON logs, so the logging shape already decided above (timestamp, request ID, user ID, tool ID, step, level, environment, duration, error fields) is natively filterable with no extra parsing work. Datadog is deferred as a genuine future iteration (e.g. a demo add-on), not built into v1.
- [x] ~~Application-level logging conventions~~ - resolved: every request logs one structured JSON entry regardless of outcome, with timestamp, request ID, user ID (from the Cognito token), tool ID, step number, level (info/warn/error), environment (dev/prod), and duration (optional - present on request-completed entries, absent on request-started entries, since duration isn't known until the request finishes). Error-level entries additionally carry the five error-handling fields already defined (code, user-friendly message, developer explanation, stack trace, runbook link). One consistent shape across success and failure logs keeps them easy to query in CloudWatch Logs Insights.
- [x] ~~Game-state tracking between turns~~ - resolved: explicitly out of scope, not just deferred. Not being built for this project.
- [x] ~~Plugin dependency ordering~~ - resolved: informational only via an optional prerequisites list and a startHere flag on PluginTool (see Plugin interface), never enforced server-side.
- [x] ~~Request-flow and error-handling details for the Lambda handler~~ - resolved: fully specified in Architecture (Lambda handler flow, error handling paragraphs) - SDK handles the JSON-RPC envelope, list-tools and call-tool handlers, input-shape validation, and tool-level error treatment.
- [x] ~~Specific MCP SDK/framework choice~~ - resolved: official @modelcontextprotocol/sdk, McpServer, stateless Streamable HTTP with JSON responses (see Architecture).
- [x] ~~Check-in question schema~~ - resolved: stays a plain string for v1 (as in StepResult), no structured expected-answer or hint logic. Revisit if richer check-ins are needed later.
- [x] ~~ChatGPT compatibility~~ - resolved: out of scope for now. Claude is the only target client for v1; the Cognito/OAuth questions around ChatGPT's client-credentials and client-ID-metadata-document requirements are not being pursued.
- [x] ~~Teaching content sourcing~~ - resolved by the pivot to a generic board-game MCP server with Catan as the v1 reference game. Catan has no equivalent IP/AI-use restriction, so content can be written freely, including with AI assistance if desired. The plugin architecture remains content-agnostic regardless of game, so adding other games later stays possible, subject to each game's own content-sourcing constraints.
- [x] ~~Cold start~~ - resolved: listTools() runs once per cold Lambda instance and its result (metadata only, no step content) is cached in memory for that instance's lifetime, so only the first request after a cold start pays the DynamoDB query cost. Memory footprint is negligible (a few hundred bytes per tool) and doesn't compete with step content, which is fetched per-request and never cached in bulk. Acceptable for v1 given the demo traffic profile.
- [x] ~~Keeping secrets out of the cdk diff output~~ - resolved: accepted as is. The deploy workflow prints cdk diff to the run summary, and GitHub masks the exact value of any secret that appears in it. The default execute-api endpoint is disabled on the HTTP API, so the generated API URL is not a usable address and the only way in is the Route 53 domain. Credentials never appear, since OIDC issues short-lived tokens and there are no long-lived keys. The remaining risk is that GitHub masking does not catch a transformed value (base64, URL-encoded, split across lines), which could reveal the domain name or account ID. Both are low sensitivity: the domain is already public through DNS and certificate transparency records, and an account ID cannot be used to gain access. Alternatives considered and rejected for now: emailing the diff to the owner instead of printing it (extra setup and a mail secret), redacting known values with a script (only catches the forms anticipated), keeping values out of the template (not possible for account ID, region or domain, which CDK needs at synth time), and making the repo private (defeats the purpose of a public repo, and reviewer approvals are restricted on private repos on the free plan). Revisit if the live endpoint is ever abused.
